# Sprint P1.2 – Adaptive Global Tile Engine

## Scope

P1.2 replaces the single center-region query from P1.1 with a bounded,
adaptive viewport plan while preserving the production chain:

```text
Browser
→ OpenLura same-origin API
→ Cloud Run
→ Firestore Budget Gate
→ OpenSky
```

Motion, Replay, Historical Track, selection, details, favorites and filters
continue to consume the same merged provider-neutral aircraft snapshot.

## Tile plan

The visible MapLibre bounds are divided into stable, non-overlapping 4° × 4°
regions. Every backend request therefore remains exactly 16 square degrees.
Regional viewports load every visible region. When an extremely zoomed-out
viewport contains more than twelve regions, the planner selects twelve
deterministic representative regions distributed across the visible world.

This is deliberate budget protection: a complete world view contains thousands
of valid provider regions and cannot truthfully be refreshed under the anonymous
300-operation daily limit. The product reports sampled coverage rather than
claiming that every world tile is simultaneously live.

## Scheduling and budget

- At most one region request is active.
- The focus region loads immediately.
- Missing visible and adjacent background regions start center-first at a
  bounded two-second cadence, with at most one active request.
- Once all planned regions are fresh, the focus region refreshes every six
  minutes.
- The browser-session ceiling remains 240 request starts per rolling day.
- The Firestore Budget Gate remains the authoritative global limit.
- Motion never schedules a network request.

## Cache and merge

Successful region snapshots are retained in a bounded in-memory cache:

- maximum 64 regions;
- six-minute freshness window;
- thirty-minute hard expiry;
- least-recently-inserted eviction;
- aircraft duplicated across region boundaries are merged by stable ID, keeping
  the newest position timestamp.

Previously presented aircraft remain available while a new plan is loading.
Fresh regions are added progressively; after the plan completes, obsolete
regions leave the presentation. Re-visiting a fresh cached region causes no new
request.

## Product status

The compact map status distinguishes:

- regions still loading;
- loaded versus planned live regions;
- successful empty coverage;
- sampled versus total visible region count;
- memory or edge/backend cache reuse.

This keeps empty or partially loaded world views explicit without interrupting
the map.

## Known limit

At very low zoom the map displays a deterministic live sample of the visible
world, not simultaneous exhaustive global coverage. Increasing this cap would
consume the anonymous provider allowance faster and requires a separate Product
Owner decision about provider capacity or paid infrastructure.
